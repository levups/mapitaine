Mapitaine

Sitemaps for Rails.The XML files that tell search engines which pages a site has, in which languages, and when each one changed.

Each kind of page is a small class that names its records, their URLs and their languages. Mapitaine writes the hreflang links itself, cuts the sitemap into files that keep the same records from one build to the next, and rewrites only the files whose records changed.

gem "mapitaine"

Get startedBenchmarks

How it works

Add the gem (it needs Ruby 3.3 or later and Rails 8.0 or later), set the host of the site, then write one class per kind of page. Its blocks have your route helpers. bin/rails mapitaine:build writes the files and the index, and the next build rewrites only what moved.

app/sitemaps/product_sitemap.rb

class ProductSitemap < Mapitaine::Source
  scope { Product.published }
  url { |product, locale| product_url(product, locale:) }
end

A page is one record in several languages, so every language of it lists all the others and itself. Search engines ignore hreflang links that the page they point to does not return: here they cannot be written wrong. The guide covers the rest.

What you get

Languages built in

One <url> per language, each with the hreflang links of all of them and x-default. A record that exists in three languages out of twenty-four lists those three.

Languages

Files that stay put

Each file holds a fixed range of ids, so a record is in the same file at every build. The range is sized from the number of languages, to stay under 50,000 URLs and 50 MiB a file.

Files

Builds that skip what did not move

A build asks the database for the count and the latest change of each range, and compares them with the last build. One query per source, and only the files that differ are rewritten.

Building

No callback in your models

Nothing hooks into Active Record. update_all, imports and deletions are seen like any other change, because the build reads the table, not a list of events.

How a build decides

Dates that are true

lastmod is the only hint search engines still read. It is the date the content changed, in the files and in the index. priority and changefreq are not written.

The date of a page

Any bucket Active Storage reaches

Files go to public/, or through a service of config/storage.yml to S3, Google Cloud Storage or Azure, with the credentials the app already has.

Storage

IndexNow

Each build sends Bing, Yandex, Seznam and Naver the URLs that changed, appeared or went away since the previous one, and sends again what they refused. The first build sends nothing.

IndexNow

Checks without a request

mapitaine:check fails on a URL outside the hosts of the site, a URL listed twice or a date in the future. It reads what it would write, and never requests a page of the site.

Checking

720,000 URLs in half a minute

30,000 records in 24 languages build in 32 s. A build with nothing new takes 10 ms, and three changed records rewrite 2 files out of 55 in a second.

Where it comes from

Mapitaine was written for a site of about 30,000 pages in 24 languages, 720,000 URLs. At that size, a script that lists every URL again at each run spends nearly all its time on pages that did not change, and the links between languages are easy to get wrong by hand.

Sitemaps changed in the meantime. Google stopped reading priority and changefreq, the ping endpoints closed, IndexNow appeared, and an honest lastmod became the one signal worth sending. Mapitaine writes what search engines read today, and nothing else.
